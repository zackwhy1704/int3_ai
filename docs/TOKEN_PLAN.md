## 1. Sign-in flow (step by step)

The desktop app uses the system browser for sign-in (same UX as a web app; avoids
embedding a WebView with its own cookie jar). A one-time code (OTC) bridges the
browser session to the app's bearer token.

1. **User clicks "Sign in" in the Tauri app.**

2. **App opens the system browser** to:
   ```
   https://<backend>/api/auth/login?provider=google&redirect=companybrain://callback
   ```
   (or `provider=microsoft`). The `redirect` parameter is stored server-side in the
   login_attempt row; the browser never controls where it ends up.

3. **Backend runs the OIDC code flow** — identical to the web flow (PKCE, state, nonce,
   JWKS verification, RS256 only, email_verified for Google, tid:oid for Microsoft).

4. **Backend receives the ID token, creates a session** in the control DB (same
   sessions table as the web flow).

5. **Backend issues a one-time code (OTC)**:
   - 16 bytes of `secrets.token_urlsafe` (URL-safe base64, ~22 chars).
   - 30-second expiry (stored as `expires_at` in a new `desktop_otcs` control DB table).
   - Stored as its SHA-256 hash (same pattern as sessions).
   - Bound to the session's `tenant_id` and `user_id`.

6. **Backend redirects to** `companybrain://callback?code=<OTC>&tenant_id=<id>`.

7. **Tauri app receives the deep link** (via the OS protocol handler registered in
   `tauri.conf.json`).

8. **App sends `POST /api/auth/desktop/exchange`** with:
   ```json
   { "code": "<OTC>", "pkce_verifier": "<verifier>" }
   ```
   PKCE verifier is generated by the app before step 2 and stored in memory only.

9. **Backend verifies the OTC**:
   - Looks up SHA-256 of the code in `desktop_otcs`.
   - Checks `expires_at > now()` and `used_at IS NULL`.
   - Marks `used_at = now()` atomically (prevents replay).
   - Verifies the PKCE challenge stored with the OTC.

10. **Backend issues tokens**:
    - **Access token:** JWT, RS256, signed by the backend's own key (not Google's).
      Claims: `sub`, `tenant_id`, `jti` (UUID for revocation), `exp` (15 min), `iat`.
    - **Refresh token:** 32-byte random, stored as SHA-256 in `desktop_tokens` table
      with `session_id`, `tenant_id`, `user_id`, `exp` (≤8 h), `used_at`.

11. **App stores both tokens in the OS credential store** (see §3). The OTC and PKCE
    verifier are zeroed from memory.

### Loopback fallback
If `companybrain://` is not registered (first run before installer has registered it),
the backend falls back to:
```
http://127.0.0.1:<random-port>/callback?code=<OTC>&tenant_id=<id>
```
The app opens a local HTTP listener on a random port before step 2 and passes the port
in the `redirect` parameter. This is the same pattern as the current `int3_desktop`
PKCE flow but replaces the Google-direct exchange with the OTC exchange.

## 2. Token format

### Access token (JWT, RS256)
```json
{
  "alg": "RS256",
  "kid": "<backend-key-kid>"
}
{
  "iss": "https://<backend-domain>",
  "sub": "<user_id>",
  "tenant_id": "<tenant_id>",
  "jti": "<uuid>",
  "iat": <unix>,
  "exp": <unix + 900>
}
```

- Signed by the **backend's own RSA key** — NOT Google's. The backend generates and
  rotates this key; it is the only issuer the gateway and /v1 endpoints trust for
  bearer tokens.
- The backend's public key is exposed at `GET /api/auth/.well-known/jwks.json`
  (authcore caches it; kid-gated refetch with 60s debounce).
- **`jti`** is stored in a `token_revocations` table (control DB) on logout or forced
  revocation; every authenticated request checks it.
- Scope list is NOT in the token — scopes are resolved server-side per request from
  the tenant DB (same as pilot's `Principal.scopes`). The token is used only to
  establish Principal.
- **`tenant_id`** IS in the token — it identifies which DB to connect to. A modified
  `tenant_id` claim will fail the jti check and/or the DB connection.

### Refresh token (opaque)
- 32 bytes of `secrets.token_urlsafe` (~43 chars).
- Stored as SHA-256 in `desktop_tokens` (control DB):
  ```sql
  CREATE TABLE desktop_tokens (
      id_hash    text PRIMARY KEY,
      session_id text NOT NULL,
      tenant_id  text NOT NULL REFERENCES tenants(id),
      user_id    text NOT NULL,
      exp        timestamptz NOT NULL,
      used_at    timestamptz,
      rotated_to text        -- SHA-256 of the successor token
  );
  ```
- One-time use: each use inserts a new row (`rotated_to` updated) and marks the old
  one as `used_at`. A replayed refresh token is rejected.

## 3. Token storage on device

### Windows
- **Windows Credential Manager** via the `keyring` Rust crate
  (`keyring = "2"` in `Cargo.toml`).
- Credential target: `"company-brain/access_token"` and `"company-brain/refresh_token"`.
- **NOT** `tauri-plugin-store` (stores to a JSON file in `%APPDATA%`; violates the
  "never in plaintext files" invariant).
- **NOT** any write to `~/.hermes` or any file Hermes reads. Hermes never sees the
  tokens directly — it gets them through the Tauri IPC endpoint (§5).

### macOS
- **Keychain** via the same `keyring` crate (uses `security-framework` backend).
- Same credential target names as Windows.

### Invariant
Provider keys and refresh tokens are never written to disk in plaintext. Access tokens
are short-lived (15 min) and can be stored in the OS credential store without
long-term risk.

## 4. How gateway and /v1 accept bearer tokens (Phase B)

Once the backend issues its own JWTs, the gateway and /v1 routes accept:
```
Authorization: Bearer <access_token>
```

**Verification:**
1. Call `authcore.verify_async(token, audience=<backend-client-id>, jwks_url=<backend-jwks>)`.
2. `authcore` checks: RS256, iss == backend domain, aud matches, exp/iat, jti not revoked.
3. On success, returns `{sub, tenant_id}` — caller constructs a lean Principal:
   ```python
   conn = tenant_conn(tenant_id)
   user = conn.execute("SELECT id, name FROM users WHERE id = %s AND active", (sub,)).fetchone()
   scopes = [r["scope_id"] for r in conn.execute("SELECT scope_id FROM memberships WHERE user_id = %s", (sub,))]
   p = Principal(tenant_id=tenant_id, user_id=sub, scopes=scopes, ...)
   ```

**jti revocation check:**
Before constructing Principal, check `jti` against the `token_revocations` table in
the control DB. A revoked token returns 401 immediately, before any tenant DB query.

**Security property:** a forged access token (wrong issuer, wrong aud, modified
tenant_id, or revoked jti) is rejected before any DB query. Tested by the cross-tenant
suite (test_db_boundary, test_tenancy) run through this path.

## 5. Long-running agent token refresh

The Tauri app mediates all token operations. Hermes never holds a refresh token.

### Architecture
```
Hermes (Python) <--IPC--> Tauri command: get_access_token()
                                          |
                                     [check expiry]
                                          |
                              expires in <2 min?
                             /                   \
                          No                     Yes
                    return cached         POST /api/auth/desktop/refresh
                    access token          with refresh_token (keyring)
                                                |
                                         rotate refresh token,
                                         issue new access token,
                                         store both in keyring
                                         return new access token
```

### Tauri command: `get_access_token`
- Reads the current access token from the OS keyring.
- Decodes the `exp` claim from the JWT header (no signature verification needed here;
  the server will verify).
- If `exp - now() < 120s` (2 minutes), calls `POST /api/auth/desktop/refresh`.
- Refresh call sends the refresh token (from keyring) and receives a new access token
  + new refresh token.
- Stores both in keyring, returns the new access token.

### Refresh endpoint: `POST /api/auth/desktop/refresh`
```json
{ "refresh_token": "<opaque>" }
```
- Verifies the refresh token in `desktop_tokens` (by SHA-256 lookup).
- Checks `exp > now()` and `used_at IS NULL`.
- Marks `used_at = now()` and inserts a new `desktop_tokens` row (rotation).
- Issues a new access token (new `jti`, exp = now() + 15 min).
- Returns `{access_token, refresh_token, expires_in}`.

### Sign-in required event
If `POST /api/auth/desktop/refresh` returns 401 (refresh token revoked, expired, or
rotated away by another device):
1. The Tauri app emits a Tauri event: `sign-in-required`.
2. The React UI listens for this event and shows a sign-in modal.
3. Hermes receives a special response from `get_access_token` indicating unavailability
   and stops making requests until the modal is dismissed and a new token is stored.

## 6. Revocation

### Access tokens
- Short-lived (15 min), but `jti` is stored in `token_revocations` (control DB):
  ```sql
  CREATE TABLE token_revocations (
      jti        text PRIMARY KEY,
      revoked_at timestamptz NOT NULL DEFAULT now(),
      expires_at timestamptz NOT NULL    -- prune after access token lifetime
  );
  ```
- Checked on every authenticated request (index on `jti`).
- Sign-out: insert `jti` into `token_revocations`.

### Refresh tokens
- One-time use, rotation on every use.
- Sign-out: set `used_at = now()` on the active refresh token row (prevents further use
  without needing a separate revocation table).

### Sign-out: both tokens revoked
```
POST /api/auth/logout
Cookie: <session cookie> OR Authorization: Bearer <access_token>
```
- Revokes both the jti (if present) and the refresh token.
- Clears the credential store on device: Tauri calls `keyring.delete` for both entries.
- Deletes the session row from the control DB sessions table.

## 7. Scope and tenant binding

- The access token contains `tenant_id` but NOT a scope list.
- Scopes are resolved server-side on every request from the tenant DB (same as pilot's
  `Principal` — `SELECT scope_id FROM memberships WHERE user_id = %s`).
- The access token is NOT presented to the tenant DB; it is used only to establish
  which tenant DB to connect to and which user row to look up.
- **Security:** a modified `tenant_id` in the token fails the jti check (the jti was
  issued for a specific tenant_id; a mismatch is detected without trusting the claim).
  Additionally, the HMAC-derived tenant DB password means a wrong tenant_id produces
  a connection error before any data is read.

## 8. Cross-tenant suite through the bearer token path

The existing tests (`test_db_boundary.py`, `test_tenancy.py`) test the DB isolation
boundary. In Phase B, they must also pass when the request uses a bearer token instead
of a session cookie.

### How to extend the suite
1. Add a `bearer_client` fixture that calls the desktop exchange endpoint and gets a
   real access token for the test user.
2. Re-run each cross-tenant test using `bearer_client` instead of `session_client`.
3. Add a test for each forgery case:
   - **Forged issuer:** token with `iss` not matching backend domain → 401 before DB query.
   - **Forged aud:** token with wrong audience → 401 before DB query.
   - **Modified tenant_id:** sign a valid token, then modify the tenant_id claim →
     signature verification fails (RS256 signature covers all claims) → 401.
   - **Revoked jti:** sign out, then replay the access token → 401 (jti in revocation
     table).

### Invariant
A forged access token is rejected before any DB query. No tenant data is read.

## 9. What int3_desktop must change

The current `int3_desktop` sends Google id_tokens directly to the backend as Bearer
tokens. This is incompatible with Phase B.

### Files to DELETE
- `src-tauri/src/auth.rs` — sends Google id_token as Bearer; incompatible.
- Any `tauri-plugin-store` usage for token storage — uses a JSON file in `%APPDATA%`.
- Writes to `~/.hermes` for token injection — violates "never on disk" invariant.

### Files to ADD
- `src-tauri/src/keyring.rs` — Windows Credential Manager via the `keyring` crate.
- `src-tauri/src/token.rs` — Tauri command `get_access_token()` with expiry check and
  silent refresh.
- Register `companybrain://` as a deep-link URI scheme in `tauri.conf.json`:
  ```json
  {
    "plugins": {
      "deep-link": {
        "mobile": [],
        "desktop": ["companybrain"]
      }
    }
  }
  ```

### Files to REWRITE
- `src/lib/auth.ts` — currently calls Google OAuth directly. Must instead:
  1. Open system browser to backend `/api/auth/login?provider=google&redirect=companybrain://callback`.
  2. Listen for the deep-link callback (via Tauri deep-link plugin).
  3. Send `POST /api/auth/desktop/exchange` with the OTC and PKCE verifier.
  4. Store the returned tokens in keyring via the Tauri command.

### Files to UPDATE
- `Cargo.toml` — add `keyring = "2"`, `tauri-plugin-deep-link`.
- `package.json` — add `@tauri-apps/plugin-deep-link`.

## 10. Open questions for the owner

Before Phase B begins:

1. **Key rotation:** how often should the backend rotate its RSA signing key? (Suggested:
   every 30 days, with a 1-day overlap during which both old and new keys are in the
   JWKS endpoint.)

2. **Refresh token lifetime:** 8 hours (matching the session absolute timeout) or longer
   for "remember me" scenarios?

3. **Multi-device:** should one user be able to be signed in on two machines at once?
   (If yes, multiple active refresh tokens are needed; if no, issuing a new refresh
   token revokes all previous ones.)

4. **Loopback port range:** which ports are acceptable for the loopback fallback?
   Some client IT policies block non-standard ports. (Suggested: random in 49152–65535,
   with a fallback to a fixed port if the random one is taken.)

5. **Token format for Hermes IPC:** Hermes calls the Tauri `get_access_token` command.
   This is an in-process call with no network round-trip, so the token is only in memory
   during the Hermes request. Is this acceptable to the security review?
